# 寻路与拥塞处理

本目录记录代码实现和性能方案；`docs/design` 保留玩法、规则和 GUI 等游戏设计。

## 问题

大部队移动绕山时，若所有单位各自走最短路，会被同一条仅容单一单位通行的山道收敛，挤成一线并反复互相推搡。原因有二：

1. A* 只考虑地形代价，不感知其他单位的存在，各单位的最短路自然收敛到同一狭道。
2. 移动严格按"下一路径格中心"走，被避让推挤偏离后要斜回原格子中心，中心在身后就往回走，顶住后方单位，直到周期重寻路才从当前位置重新规划。

## 方案（碰撞代价 + 走廊跳过）

在不改变寻路复杂度、不增加搜索次数的前提下，三处小改动：

- **密度网格**：每逻辑步重建一张占用地图的 `Float32Array`（数组复用原地清零），统计每个格子上存活的地面单位数量。供寻路代价与移动减速共用。
- **A* 拥挤代价**：寻路时目标格密度超过 1（排除自身）后，按 `CROWD_K`（0.7）叠加通行代价，`CROWD_CAP`（4）封顶代价。存在替代路线时自动分流，只有一条路时不会无谓绕远。分流靠"密度反馈 + 周期重寻路"随时间自然形成，不使用随机扰动。
- **移动减速 + 路径走廊跳过**：同格超过 2 个单位时按密度降速（下限 55%），窄口形成车流式通行。单位被挤偏后若仍在"当前路点→下一路点"线段旁的走廊内（0.5 格），直接跳过当前路点、顺着前方路点继续走，不再往回够原格子中心。

## 性能账

- `updateDensity` 每步 O(格子数 + 单位数)，数组复用不再分配内存。
- A* 每次展开仅在原有基础上多一次密度数组读取（实测单次寻路约 +6%，不改变搜索节点数）。
- `move` 每单位每步做一次密度读取；走廊跳过通常第一轮即退出。

**微基准**（128×88 均衡地图，25 单位）：密度重建约 1.8µs/步；单次带密度寻路约 115µs，无密度约 108µs。

**宏观对比**（改动前提交 vs 当前，9 轮取中位数）：demo −0.3%、进攻大部队移动 −2.5%、均衡大部队移动 +4.2%、均衡长局 +2.9%，均落在 ±5% 运行噪声内，无统计显著差异。

## 验证

- 既有测试全部通过（core/balanced/performance/refactor）。
- 均衡地图 12 单位横穿全图可正常到达目标并转为待机，无卡死。
