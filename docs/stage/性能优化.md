# 性能优化方案

状态：已完成只读调查，以下任务尚未授权实施。目标是在不降低 20 Hz 逻辑精度的前提下减少主线程尖峰，并为 [3D 渲染阶段方案](3d设计.md) 的 120 FPS 目标提供余量。

## 当前判断与测量

- 当前进攻关约 277 个单位、18 座建筑、128 × 88 地图。现有模拟能维持 50 ms 逻辑步；主要风险是视野或群体寻路集中执行时占用 120 Hz 画面帧的 8.33 ms 预算，并非平均模拟吞吐量不足。
- 本机 Node 粗测中，进攻关 400 步平均约 3.34 ms/步，集体进攻约 3.94 ms/步。一次视野更新约 5.0～5.2 ms；单位更新约 1.1～1.5 ms/步；单位分离约 0.4～0.5 ms/步。
- 400 步中约调用 11.2 万次 `acquireTarget`，无目标待机单位按当前逻辑几乎每步重新索敌。集体移动还会让大量单位独立 A* 与周期重寻路。
- 下表是人工密集场景的 120 步粗测，不含浏览器、GPU 和 3D 渲染，只用于观察规模增长趋势，不作为实际 FPS 结论。

| 单位数 | 平均逻辑步 | 单次视野更新 | 单位更新/步 | 分离/步 |
| ---: | ---: | ---: | ---: | ---: |
| 200 | 3.81 ms | 2.59 ms | 1.87 ms | 0.46 ms |
| 500 | 9.47 ms | 5.85 ms | 5.24 ms | 1.14 ms |
| 1000 | 20.48 ms | 13.11 ms | 12.00 ms | 2.33 ms |

## 实施顺序

1. [ ] 建立浏览器性能基线：分别记录逻辑、渲染、GPU、GC、draw calls、平均 FPS 与低分位帧时间；固定目标电脑、浏览器、分辨率、场景和随机种子。
2. [ ] 将地面视野改为每阵营一次多源加权 Dijkstra；保留空中圆形视野，并与当前逐单位参考算法逐格对照。
3. [ ] 为 A* 缓冲增加 generation stamp，只初始化本次访问格，避免每次搜索整图 `fill`；结果必须与当前路径一致。
4. [ ] 将无目标自动索敌改为分批错峰更新；已有目标验证仍保持每步执行，并补充受击、手动攻击和近敌出现的立即扫描路径。
5. [ ] 用明确的通行版本替代反复拼接建筑签名，并评估持久 `entityById`、阵营列表及空间索引，减少每步全量重建和临时对象。
6. [ ] 将完整 `Game` 模拟迁入一个 module Web Worker；主线程保留输入、HUD 和渲染，通过前后状态插值显示 120 Hz 画面。
7. [ ] 在 500～1000 单位压力测试仍不达标时，验证群体共享路径/flow field、持久空间桶和局部或降频分离。
8. [ ] 只有在算法、Worker 和数据复用完成后仍存在已确认热点，才评估 SharedArrayBuffer、数据导向/ECS 或 WASM；不以 WebGPU compute 作为当前逻辑优化方案。

## 设计边界

### 浏览器性能基线

- Node 基准只测模拟吞吐量，不能替代浏览器主线程与 GPU 测量。
- 记录普通进攻、全军下令、密集交战、视野刷新、快速镜头移动和大量弹道；比较改动前后最终快照，不能用减少模拟工作换取提速。
- 120 FPS 以 8.33 ms 为帧预算，同时观察 1% low 和最长帧，不能只报告短时平均 FPS。

### 多源视野

- 每个地面视野来源以 `-侦测预算` 作为初始距离，同阵营来源进入同一个优先队列；格子的最小结果不大于 0 时可见。
- 保留地形进入代价、双方隔离、已探索记忆、飞行单位森林规则、暴露效果与 `updateGhosts` 时序。
- 验证混合地形、地图边缘、原地修改地形、地图替换、同格不同预算及双方最终视野数组。
- 第一阶段不降低当前约 0.15 秒的视野更新频率；先通过算法减少周期性尖峰。

### A* 缓冲与群体寻路

- 为 `g`、`closed` 和必要的父节点状态增加搜索代数，只重置实际访问过的格子；保留当前目标修正、斜角通行、山林偏好与密度代价。
- 建筑新建、实际占地、摧毁、拆除和地图替换时递增通行版本；施工预定尚未占地时不得提前阻挡。
- flow field 属于后续行为级优化：静态地形与建筑可共享反向距离场，单位仍保留阵型落点及局部避让。不同山林通行偏好分开缓存，动态密度不应迫使整场每步重建。

### 索敌与更新频率

- 无目标单位候选方案为 0.10～0.15 秒扫描一次，并按单位 ID 或稳定调度槽错开；最大自动警戒延迟需先确认可接受。
- 有效目标、射程、冷却、攻击、移动和弹道保持 20 Hz；不能把整个模拟降到 10 Hz。
- 防守 AI 当前约 2 秒一次、均衡 AI 约 3 秒一次，已有降频，不列为优先热点。
- 分离先保持 20 Hz；只有 500+ 单位实测仍明显时，才比较 10 Hz、只处理移动单位或脏空间桶，并验证拥挤稳定性。

### Worker 架构

- 一个模拟 Worker 统一拥有 `Game`、AI、视野、寻路和战斗，避免多个 Worker 共享可变战局造成同步开销。
- 主线程向 Worker 发送玩家命令；Worker 以 20 Hz 推进并返回精简快照；主线程保存相邻快照并插值位置、朝向和弹道。
- 第一版先测普通 structured clone；如复制和 GC 成为热点，再使用可转移 `ArrayBuffer` 双缓冲。只有传输仍成为明确瓶颈时才考虑 `SharedArrayBuffer` 及服务器隔离头。
- 3D 渲染仍留在主线程；首版不使用 OffscreenCanvas 搬迁 Babylon 渲染，避免增加 DOM HUD、拾取和调试复杂度。
- Worker 只隔离主线程卡顿，不会减少算法总工作量，因此应在主要算法热点处理后实施。

### 暂不采用的方向

- 不因当前规模改用 Rust/WASM、Unity/Godot 或全面 ECS；这些方案不能自动消除重复视野、索敌和寻路。
- 不将 AI、视野、寻路拆成多个独立 Worker，也不把逻辑迁移到 WebGPU compute。
- 不通过降低目标单位数量、删除既有规则或放宽快照一致性获得性能数字。

## 建议更新频率

| 系统 | 建议频率 |
| --- | ---: |
| 渲染与镜头 | 最高 120 Hz |
| 单位移动、已有目标验证、命中与弹道 | 20 Hz |
| 无目标自动索敌 | 6.7～10 Hz，分批错峰 |
| 视野 | 约 6.7 Hz，先优化算法 |
| 单位分离 | 先保持 20 Hz |
| 防守 / 均衡 AI | 保持当前约 0.5 / 0.33 Hz |
| HUD 与非即时面板 | 5～10 Hz |
| Worker 动态快照 | 20 Hz，渲染侧插值 |

## 验证与停止条件

- 每项先增加专项正确性检查，再运行完整 `npm test`；性能场景必须与改动前保持相同随机种子、命令、步数和最终快照。
- 视野、A* 缓冲和缓存版本属于结果等价优化；索敌错峰、分离降频和 flow field 可能改变时序或路线，必须单独获得玩法确认并记录差异。
- 先验证 277 单位现行进攻关，再测 500 和 1000 单位；浏览器阶段同时覆盖 1080p、1440p 和高 DPI。
- 当目标机器上 200～300 单位普通战斗的主要帧稳定在 8.33 ms 内、逻辑尖峰不再明显阻塞渲染，且 500 单位至少稳定 60 FPS 时，可停止扩大优化范围。
